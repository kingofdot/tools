## 2. 별표 JSON의 기본 스키마

각 파일은 루트가 오브젝트이고 `별표내용`에 항목 배열이 들어 있습니다.

```json
{
  "별표번호": "0007",
  "별표가지번호": "00",
  "별표구분": "별표",
  "별표제목": "폐기물 처리업의 시설·장비 및 기술능력의 기준(제28조제4항 관련)",
  "별표시행일자": "20250728",
  "별표내용": [ ... 항목들 ... ]
}
```

### 항목(item) 스키마

```ts
type Item = {
  depth: number          // 0 = 최상위 헤더, 1~5 = 하위
  type: 'title' | 'number' | 'korean' | 'letter' | 'roman' |
        'note-header' | 'note-body' | 'table' | ...
  marker: string         // "1.", "가.", "①", "비고" 등 원본 마커
  text: string           // 원문 그대로 ("가. 보관시설: 1일 처리능력의 …")

  // 태그/답변 (작업 완료된 항목만)
  answer?: string        // 준수계획란에 찍힐 내용. {{slotName}} 치환 대상 포함 가능
  tags?: {
    category?:     string[] | null   // 예: ["W02"]
    bizType?:      string[] | null   // 예: ["IR","FR","RTR","RREC","IFD","FFD"]
    wasteClass?:   string[] | null   // 예: ["G","I","M","L","S"]
    wasteCode?:    string[] | null   // 예: ["51-01-01"]
    action?:       string[] | null   // 예: ["CT","ST","ID","FD","RCY","IN"]
    rCode?:        string[] | null   // 예: ["R-1","R-4-1"]
    facilityType?: string[] | null   // 예: ["kiln","incineration"]
  }

  // 메타 플래그
  isHeader?:   true       // 섹션 헤더 (굵게 표시, 선택 UI에서는 카드 아님)
  noWord?:     true       // 워드 출력에서 제외 (이미 다른 항목에 흡수된 텍스트 등)
}
```

표(`type: 'table'`) 항목은 별도 구조를 가지므로 이번 버전에서는 **`별표내용` 중 table은 스킵하거나 단순 텍스트 변환으로 처리**하고, 나중에 확장하세요. (참고: build.js는 table도 렌더하지만 구조가 복잡합니다.)

## 3. 태그 체계 — `상황코드_코드표.json`

워드에 어떤 항목을 담을지는 **사용자 입력(허가/신고 유형, 폐기물, 행위, 시설 등)** 과 **항목 태그**의 교집합으로 결정됩니다. 코드-레이블 매핑은 전부 이 파일에 있습니다.

```
코드표
 ├─ category:    W01=허가, W02=신고, … (상위 분류)
 ├─ bizType:     IR=중간재활용업, FR=최종재활용업, CR=종합재활용업,
 │               IFD=중간처분업, FFD=최종처분업, CFD=종합처분업,
 │               RTR=수집운반신고자, RREC=재활용신고자, …
 ├─ wasteClass:  G=사업장일반, I=사업장지정, M=의료, L=음식물, S=생활, H=건설
 ├─ wasteCode:   허가증·신고증 기재용 6자리 코드 (51-01-01 등)
 ├─ action:      CT=수집운반, ST=보관, ID=중간처분, FD=최종처분, RCY=재활용, IN=그 외
 ├─ rCode:       재활용 R코드 (R-1~R-9, 하위 R-4-1 등)
 └─ facilityType: kiln, incineration, landfill, … (시설별 기준 필터링에 사용)
```

`그룹` 키가 있으면 드롭다운에서 그룹핑에 사용하세요. 예: `facilityType.그룹`은 소각/매립/재활용별로 묶여 있음.

### 필터 규칙 (중요)

한 항목이 워드에 **포함되려면** 모든 태그 차원에서 다음 조건을 만족해야 합니다:

- 항목 태그가 `null`이면 → 그 차원은 **항상 통과** (무관한 항목이란 뜻)
- 항목 태그가 `[...]`이면 → 사용자가 선택한 값 중 **하나라도 겹치면 통과**
- 한 차원이라도 겹치지 않으면 → 해당 항목 **제외**

의사코드:

```python
def passes(item_tags, user_selection):
    for dim in ['category','bizType','wasteClass','wasteCode','action','rCode','facilityType']:
        item = (item_tags or {}).get(dim)
        user = user_selection.get(dim) or []
        if item is None:           # 항목이 해당 차원을 신경 안 씀
            continue
        if not user:               # 사용자 선택 없음 → 통과
            continue
        if not set(item) & set(user):
            return False           # 교집합 공집합 → 제외
    return True
```

예외: `isHeader=true` 항목은 자기 자신의 태그가 아니라 **자식이 하나라도 통과했을 때** 포함합니다 (섹션 제목).

## 4. answer 슬롯 치환

`answer` 값에 `{{slotName}}` 형태가 있으면 사용자 입력/마스터 데이터로 치환해야 합니다. 정의는 `docs/별표7_슬롯목록.md`, `docs/별표17_슬롯목록.md` 참고.

슬롯 명명 규칙: `<종류><Spec|VehicleNo|…>_<Scope>`

- Scope 접미: `_Gen`(생활) / `_Ind`(사업장) / `_Haz`(지정) / `_Med`(의료) / `_Notif`(신고자)
- 자주 쓰는 것:
  - `{{ctVehicleNo_Ind}}` — 수집운반 차량등록번호 (사업장)
  - `{{storageSpec_Ind}}` — 보관시설 사양
  - `{{recyclingSpec_Notif}}` — 재활용시설 사양 (신고자)
  - `{{contactAddr}}` — 연락 사무실 주소

별표5의4에서는 `{applicable: "...", notApplicable: "..."}` 객체를 쓰기도 합니다. 이 경우 사용자가 "해당"을 고르면 `applicable`, 아니면 `notApplicable`을 선택. 그 안의 `{slot}`(단중괄호)도 치환.

치환 순서:
1. 이중 중괄호 `{{...}}` 먼저
2. applicable/notApplicable 객체 해결
3. 그 결과의 단일 중괄호 `{...}`

슬롯 값이 비어 있으면 빈 문자열로 둡니다(에러 X).

## 5. 워드 레이아웃

기본은 **별표 단위 1개 표**, 2열 구조:

```
┌──────────────────────────────────────────────┐
│  별표 제목 (bold, 18pt)     <사용자 코드>    │    ← 표 전체 폭 span
│                  부제 (bold, 22pt, 가운데)    │
├──────────────────────────┬───────────────────┤
│  기준 (가운데, bold)     │ 준수계획 (가운데) │    ← subheader
├──────────────────────────┼───────────────────┤
│  item.text               │ item.answer       │    ← 각 행
│  (depth × 150 들여쓰기)  │                   │
├──────────────────────────┼───────────────────┤
│  …                       │ …                 │
└──────────────────────────┴───────────────────┘
```

### 행 렌더 규칙

- `depth × 150` twip(또는 python-docx의 `Emu/Pt`에 해당 단위) 만큼 왼쪽 들여쓰기
- `isHeader=true` → 폰트 크기 21pt, **굵게**; 일반 항목은 20pt
- 텍스트는 `marker + " " + text`가 아니라 **`text` 그대로** (마커는 원문에 이미 포함)
- 답변(오른쪽 셀)은 일반 폰트
- 줄 사이 테두리는 생략(NIL), 표 바깥 테두리만 굵게

### 코드 태그 문자열

사용자가 선택한 조건은 표 상단에 `<코드>` 한 줄로 요약해 찍습니다. 예:
```
<W02-RREC-I-RCY-R4>
```
규칙: `category-bizType-wasteClass-action-rCode` 순, 비면 건너뜀. build.js의 `buildCode()`를 참고.

### 별표가 여러 개일 때

각 별표는 **새 표**로 만들고 표 사이에 빈 `Paragraph` 하나(spacing before/after 200) 삽입.

## 7. 구현 스택 제안 (이 프로젝트 기준)

- `python-docx`로 작성
- 표 = `doc.add_table(rows=N, cols=2)` → 첫 2행 병합으로 헤더
- 셀 여백/테두리는 `docx.oxml.ns.qn('w:tcBorders')` 직접 XML 삽입
- 들여쓰기 = `paragraph.paragraph_format.left_indent = Pt(7.5 * depth)` 정도
- 굵게/크기 = `run.bold = True`, `run.font.size = Pt(10.5)` 등

build.js의 폰트 크기 `size: 20` / `size: 21`은 docx.js 단위(half-point, 즉 10pt / 10.5pt)입니다. python-docx에선 그대로 `Pt(10)`, `Pt(10.5)`.

## 8. 데이터 무결성 주의사항

- **부모-자식 통합 답변**: 부모가 `answer`를 가지면 자식은 `answer=null`일 수 있음. 자식을 따로 렌더하지 말고 부모만 찍어야 할 때가 있음. `isHeader`가 아닌데 자식이 비어 있으면 상속 확인.
- **삭제 표기**: `text`가 "삭제 <YYYY.MM.DD>"이거나 `noWord=true`인 항목은 절대 출력 금지.
- **별표7 시설·장비·기술능력 표**: `type: 'table'` 원시 데이터는 그대로 꺼내 `<table>`로 그려야 합니다. 본 지침 v1은 스킵.

## 9. 빠른 시작 (pseudo)

```python
# 1) 로드
items = {src: json.load(open(f'enforcement_rule/{src}.json'))['별표내용']
         for src in SOURCES}
codes = json.load(open('docs/상황코드_코드표.json'))['코드표']

# 2) 사용자 선택 받아 필터
picked = {src: [it for it in arr if passes(it.get('tags'), user)] for src, arr in items.items()}

# 3) 별표별로 표 생성
doc = Document()
for src, arr in picked.items():
    add_header_table(doc, meta[src], user_code_string)
    for it in arr:
        if it.get('noWord'): continue
        add_row(doc, text=it['text'], answer=fill_slots(it.get('answer',''), user),
                depth=it['depth'], is_header=it.get('isHeader', False))
    doc.add_paragraph('')

# 4) 저장
doc.save('compliance_' + user_code_string + '.docx')
```

## 10. 리스크/알려진 이슈

- 태그가 `null`인 항목이 많아 필터가 과하게 통과할 수 있음 → 사용자 선택은 **최소 1개 이상** 강제
- 별표5의4의 `{applicable/notApplicable}`은 UI에서 "해당/비해당" 체크박스가 필수
- 별표7 표 항목은 별도 구현 필요 (위 v1 스킵 정책과 충돌 시 확장)
